# conformance-allow.txt -- the static ratchet for protoJS.
#
# Format: <check-id> <path>:<line> <sha1-12-of-the-line-text> :: <justification>
# A <path>:* entry with a * hash covers WARNINGS ONLY in that file; an error must
# be justified site by site, so a blanket entry can never hide a real defect.
#
# Run: python3 ../protoCore/scripts/conformance/check_static.py --repo .
# Exit 0 clean, 1 an unjustified finding, 2 a stale entry.
#
# THIS FILE EXITS 1 ON PURPOSE, with ONE uncovered error.  It is left uncovered
# so the check keeps failing until it is answered.
#
#   GCBridge.cpp:676 -- external_finalizer.  A fromExternalPointer with a NULL
#   finalizer, whose comment says the pointer is not owned.  Probably legitimate,
#   but it is a checklist C7 question nobody has answered, and the check says in
#   its own message that it cannot rule on it.  See docs/CONFORMANCE.md.
#
# IT WAS FOURTEEN UNTIL 2026-09-26.  Thirteen were fixed, not allowlisted, and the
# allowlist below is unchanged at 217 entries with 0 stale.  For the record of what
# they were and why they mattered, see docs/CONFORMANCE.md, which keeps the original
# analysis:
#
#   SEVEN external_finalizer errors (f708dc3fc..50fe92b1b).  Five finalizers joined
#   OS threads, released ProtoRootSet pins and in one case destroyed a second
#   ProtoSpace, all ON THE SINGLE GC THREAD INSIDE THE SWEEP.  Each now does only
#   the non-blocking half -- close the descriptor, flip the flag -- and records the
#   orphan (src/GcOrphanQueue.h); a mutator thread does the rest.  Where an owner
#   can relinquish explicitly, it does: serverClose, socketDestroy, workerTerminate.
#
#   SIX blocking_join_unbracketed errors (50fe92b1b, f5d332c3a).  Two were on
#   genuinely registered threads -- ThreadPoolExecutor::shutdown and shutdownNow,
#   reached from ~JSContextWrapper on the main thread -- and are now bracketed, the
#   guard covering the condition wait as well as the join loop.  The other four were
#   the joins inside the finalizers above, i.e. the GC thread, which is NOT in
#   runningThreads; there an UnmanagedScope would be a no-op at best, so the join
#   moved off the finalizer instead.
#
#   The inconsistency that made these findings rather than oversights -- the same
#   teardown helpers bracketed when called from JavaScript and not from the
#   finalizer -- is gone: the guard now lives inside the helper, so both callers
#   share it and a new caller cannot forget it.
#
# Do not add an entry here to silence a finding.  Thirteen of fourteen were closed by
# fixing the code and the fourteenth is a question, not a defect to launder.
