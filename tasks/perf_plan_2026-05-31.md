# Performance Work Plan — Closing the QuickJS Gap

**Baseline**: 2026-05-31, `build_release/protojs` against vanilla QuickJS (deps/quickjs).
**Geomean today**: QuickJS 10.34× faster than protoJS over 11 benchmarks.
**Goal of this cycle**: bring the geomean below 5× on the same suite without
losing the parallel_cpu advantage (currently 14.92× protoJS).

This plan is derived from `perf record` profiles of ten standard benchmarks
(`tests/benchmarks/standard/*.js`).  Symbol percentages aggregated weighted by
each benchmark's protoJS wall time.

## Methodology

```
PROTOCORE_GC_CONTEXT_THRESHOLD=1000000000 \
  perf record -F 999 -o <bench>.data -- \
    build_release/protojs tests/benchmarks/standard/<bench>.js
```

- **GC suppressed via `PROTOCORE_GC_CONTEXT_THRESHOLD=1e9`**.  The default
  threshold is 10 000 cells per context; raising it to 10⁹ effectively
  disables per-context GC submissions for any benchmark in this suite.
  Memory ceiling is not hit (system has 46 GB available; the heaviest
  bench, `object_write_only`, allocates roughly 30M cells × 64 B ≈ 2 GB).
- **GC runs on its own thread** in protoCore.  Without suppression the
  GC thread's mark/sweep cycles would contaminate the measurement with
  samples that are not part of what the JS code is doing.  Verified
  post-hoc: main thread holds **98 % of all samples**; worker and GC
  threads contribute 10–13 samples each (residual scheduler noise).
  **GC-pressure analysis is deliberately deferred to a separate
  session** so it does not confound the per-symbol attribution here.
- `perf record -F 999`, `perf report --no-children`, top symbols at
  `--percent-limit 0.3`, weighted by `(pct/100) × bench_total_ms` and
  summed across the suite.
- Raw perf data: `/tmp/protojs_perf_nogc/*.data` (preserved for
  re-baselining after any landed PR).

Top 25 symbols account for **51.7 %** of total wall time.  Three
structural patterns dominate:

1. **Allocation chain** — `allocCell + addCell2Context + getFreeCells +
   Cell::Cell + implAllocCell + Cell::operator new + kernel zero-fill` ≈
   **~21 %** of total wall time.  Pervasive: every object/property/list
   creation pays into this bucket.
2. **AVL list operations** — `ProtoListImplementation` ctor + `implInsertAt`
   + rebalance bucket ≈ **~12 %**.  Concentrated in `object_write_only`,
   `array_literal`, `json_transform`, `object_property`.  Every list
   mutation builds a new node and rebalances; structural sharing makes
   it impossible to mutate in place.
3. **Interpreter dispatch** — `runBytecode` ≈ **5 %** aggregate but
   bimodal: **48–53 %** in `numeric_loop` and `control_flow`, **2–5 %**
   in allocation-bound benches.  Already heavily optimised by
   P-JS-{0..7}; further gains here require specialised fast paths for
   arithmetic / compare opcodes, not generic dispatch work.

A fourth pattern visible only in `string_concat`: **rope structural-walk
checks** (`isStringInternalNode`, `isStringLeafNode`, `nodeHeight`,
`byteCount`, `charCount`, `subtreeHash`) sum to **~36 %** of that single
benchmark, attributable to repeated `Cell` type-introspection on every
rope-node walk.

The geomean is dragged most by right-of-the-table benches with both

`array_literal`).  These are all allocation-bound and AVL-bound, not
dispatch-bound.  Central insight: **the largest remaining single-thread
gains are in protoCore, not the interpreter**.

## The Five Optimisations

Each entry: target, mechanism, expected yield, risk, prerequisites, and
the concrete first PR.  Ordered by expected absolute wall-time reduction.

### P-JS-8 — Cell allocation fast path

**Target symbols**: `allocCell` (6.67%) + `addCell2Context` (1.79%) +
`getFreeCells` (2.94%) + `Cell::Cell` (1.39%) + kernel zero-fill (6.69%
shared with this path) ≈ up to **~14 % of total wall time** addressable.

**Current behaviour**: `ProtoContext::allocCell()` calls `getFreeCells`
to ensure a non-empty cell freelist, pops one, then `addCell2Context`
threads it into the per-context young-chain, then `Cell::Cell` runs to
initialise tag bits and `next_and_flags`.  All four functions are
independent symbols in the profile — the call chain itself is the cost,
not any single body.

**Mechanism**:

1. **Inline fast path on context**: `allocCell` becomes a header-inline
   function that pops from `ctx->localFreelist` in one move, falls back
   to an out-of-line `slowAllocCell` only when the freelist is empty.
   Saves ~3 cycles per allocation (call + branch + ret) and removes a
   barrier to LTO inlining of `Cell::Cell`.
2. **Fuse `addCell2Context` into the inline path**: the link-into-young-
   chain is a single pointer store.  The call-site already has the
   context; no reason to be a separate function.
3. **Pre-bumped young chain**: maintain a small bump-pointer region in
   each context for the next N allocations.  When exhausted, refill
   from the per-thread chunked freelist (task #36 already provides O(1)
   chunked refill).
4. **Lazy `Cell::Cell` initialisation**: `next_and_flags` is overwritten
   immediately by every concrete cell type's own initialiser.  The base
   ctor's stores are dead in the common case — remove via tagged
   dispatch from the concrete ctors.

**Expected yield**: 5–8 % of total wall time recoverable.  Visible on
every allocation-bound benchmark; biggest single-bench impact on
`object_write_only` (currently ≥ 21 % of its time in this chain).

**Risk**: low.  Well-understood paths.  Chunked freelist exists (task
#36); this is refinement, not new mechanism.  Main risk is correctness
on contention paths — the inline fast path must not race the GC thread.

**Prerequisites**: none.  Self-contained in protoCore.

**Concrete first PR**: header-inline `allocCell` + fuse
`addCell2Context`.  Measure on `object_write_only` and `array_literal`.
If geomean ratio vs QuickJS drops by ≥ 0.5×, land the change and
proceed to steps 3 and 4 in follow-up PRs.

### P-JS-9 — ProtoList AVL write-path specialisation

**Target symbols**: `ProtoListImplementation` ctor (6.47%) + `implInsertAt`
(2.84%) + rebalance bucket (2.95%) + `implGetAt` (1.16%) ≈ **~13 % of
total wall time** addressable, with most concentrated on
`object_write_only`, `array_literal`, `json_transform`.

**Current behaviour**: every list mutation allocates a fresh
`ProtoListImplementation` AVL node, recursively rebuilds the path from
root to leaf, and rebalances by left/right rotations where heights
diverge.  Structural-sharing discipline means an N-element list pays
O(log N) allocations per mutation, with a balanced-tree constant of
~1.4×.  For `array_literal`'s 100 k-element build-up, that's roughly
100 k × 17 ≈ 1.7 M allocations — and dominates the absolute time.

**Mechanism**:

1. **Append-at-end detection**: most JS array building is monotonic
   append (`a.push(x)`, `a[a.length] = x`, `for (i…) a[i] = i`).  In
   that pattern the rightmost path of the AVL is rebuilt on every
   insert.  Specialise: detect "insert at index ≥ size", maintain a
   pointer to the rightmost spine, append by extending only the spine
   cells instead of full path-copy.  O(log N) → O(1) amortised for
   monotonic append.
2. **SmallList inline form** (analog to SmallSparseList): lists with
   ≤ 4 elements live entirely in a single cell, no internal tree.
   Promote to full AVL only on the 5th element.  Common in function
   arguments, small literals, tuple-like patterns.
3. **Lazy rebalance**: don't rotate on every mutation.  Track height
   skew; rotate only when it exceeds a small threshold (e.g., 3).
   Worst-case operation depth grows slightly; the constant on the hot
   common case drops.

**Expected yield**: 5–7 % of total wall time.  `object_write_only`
should drop from 158× to ~80–100× vs QuickJS (still bad, but real).
`array_literal` and `json_transform` get proportional gains.

**Risk**: medium.  Touches structural-sharing invariants.  Must
preserve: all readers see consistent snapshots; concurrent GC mark
stays correct; existing immutable-form invariants of ProtoList are not
broken by the SmallList specialisation (returning Small or AVL
depending on size is OK because both implement the same `ProtoList`
interface).

**Prerequisites**: P-JS-8 not strictly required, but the gain from
P-JS-9 is larger if every allocation is cheaper.  Land P-JS-8 first.

**Concrete first PR**: SmallList inline form for ≤ 4 elements.  Most
localised of the three steps and on its own should produce a measurable
wedge in `function_calls` and `array_literal` early-build.

### P-JS-10 — Object write specialisation (shape-aware put_field)

**Target symbols**: `resolvePutFieldOOP` (0.80% aggregate, much higher
locally) + `ProtoObject::setAttribute` (0.37%) + the upstream allocation
chain attributable to writes ≈ **3–4 % of total wall time** addressable,
with strong concentrated impact on `object_write_only` (and indirectly
on every benchmark that mutates objects).

**Current behaviour**: every property write walks the prototype chain
to detect setters/accessors, allocates new attribute storage if the
slot shape changes, and updates the attribute cache.  For repeated
writes to the same object with the same key, the work is mostly
redundant — the slot and shape don't change between writes.

**Mechanism**:

1. **Per-call-site shape cache** (inline-cache style): each
   `OP_put_field` bytecode site caches `(receiver_shape, key,
   slot_index_or_setter_ref)` from its first successful write.
   Subsequent writes that match the cached shape short-circuit to a
   direct slot write.
2. **Shape transitions as identity**: assign each distinct attribute-
   set shape a stable identifier; cache comparisons become pointer-
   equality on shape, not deep walks.  Closer to V8 hidden classes.
3. **Monomorphic write hot path**: when the cache is monomorphic (one
   shape only), inline the direct slot store into the bytecode
   dispatch.

**Expected yield**: 3–5 % of total wall time, concentrated in
`object_write_only` (could shave 20–40 % of that single benchmark's
time).

**Risk**: medium-high.  Shape transitions and inline caching are
substantial work — easy to get subtly wrong on edge cases (proxies,
getters/setters added mid-flight, prototype-chain changes).
Mitigation: cache only the simplest monomorphic case in the first PR,
fall back to the existing path for everything else.

**Prerequisites**: P-JS-8 and P-JS-9 land first.  Inline caches need
shape-id assignment infrastructure, naturally adjacent to the AVL
specialisation in P-JS-9.

**Concrete first PR**: shape-id assignment + monomorphic inline cache
for `OP_put_field` only (not yet `OP_define_field` or
`OP_put_array_el`).  Measure on `object_write_only` — if the gap drops
by 30 %+ in that single benchmark, expand to the other write opcodes.

### P-JS-11 — String rope tag-bit fast paths

**Target symbols** (string_concat-local): `StringInternalNode::fromObject`
(7.7%), `isStringInternalNode` (7.4%), `nodeHeight` (6.3%),
`isStringLeafNode` (5.9%), `byteCount` (4.1%), `charCount` (3.5%),
`subtreeHash` (1.8%) — sum to **~36 %** of `string_concat`.

Aggregate impact is smaller (~3 % of total wall time) but **highly
concentrated**: closes the string-heavy gap dramatically with bounded
work.

**Current behaviour**: every walk down a string rope (for concat,
indexing, length, iteration) recursively asks "is this an internal node
or a leaf?", "what's the byte count of the left subtree?", "what's the
height?".  Each question is a virtual-ish call that dispatches on the
cell's tag plus a structural read.  In `string_concat` building a 50 k-
rope, each new concat does a rebalance walk that asks these questions
O(log N) times per leaf.

**Mechanism**:

1. **Stash precomputed height, byteCount, charCount in the cell
   header**: rope-internal cells have spare header bits (the cell is
   64 bytes; the rope ctor uses ~16 bytes for left/right pointers).
   Pack a `height:6` + `byteCount:30` + `charCount:30` triple into a
   header word, set at construction.  All walks become field reads, no
   recursion.
2. **Tag-bit type discrimination**: `isStringInternalNode` /
   `isStringLeafNode` become a single tag check on the cell header,
   not a v-table-style dispatch.  Tag bits are already partially used
   for type discrimination; extend the scheme to rope-node forms.

**Expected yield**: 30–40 % improvement on `string_concat` (≈ 0.5–1 %
of total wall time, but a focused win — gap drops from 28× to ~16–20×
vs QuickJS on that bench).  Mild positive impact on `tree_traversal`,
`object_read_only`, `object_property` which also do string-tag work in
attribute lookups.

**Risk**: low–medium.  Self-contained in protoCore's string rope code.
Main correctness concern: precomputed counts must be invalidated /
recomputed correctly on every structural transformation (rare —
ropes are immutable and structural sharing makes new nodes with fresh
counts at creation).

**Prerequisites**: none.  Independent of P-JS-8/9/10.  Can be done in
parallel with the allocation work.

**Concrete first PR**: pack precomputed counts into cell header for
rope-internal nodes only.  Update the four hottest accessors
(`nodeHeight`, `byteCount`, `charCount`, `isStringInternalNode`).
Measure on `string_concat`.

### P-JS-12 — Interpreter arithmetic / compare opcode fast paths

**Target symbols** (numeric_loop / control_flow-local): `runBytecode`
(50.5% / 48.9%), `stackPush`/`stackPop`/`getSlot`/`setSlot` (2–11 %
each), `toTempBignum` (3.7% in control_flow), `Integer::compare`
(1.5%), `toBool` (1.7–2.7%).

Aggregate impact ~5 % across the suite but **dominant** in the two
benchmarks (numeric_loop, control_flow) closest to parity with
QuickJS.  Closing this gap moves both to true parity or better.

**Current behaviour**: integer arithmetic in tight loops dispatches
through `runBytecode`'s generic add/sub/lt/le opcodes which call
`toTempBignum` to materialise a working bignum, perform the operation,
materialise the result.  Even when both operands are SmallInteger
(tagged), the path goes through the full bignum conversion.
Comparison opcodes similarly go through `Integer::compare` rather than
a direct tagged compare.

**Mechanism**:

1. **SmallInteger fast path in arithmetic opcodes**: `OP_add`,
   `OP_sub`, `OP_lt`, `OP_le`, `OP_eq`, `OP_neq` check
   `isSmallInt(a) && isSmallInt(b)` first — if both, do the arithmetic
   on tagged values directly and re-tag.  Skip `toTempBignum` entirely.
   Overflow checks via compiler builtins (`__builtin_add_overflow`).
   Fall back to the existing path on overflow or non-int operand.
2. **Inline stackPush/stackPop/getSlot/setSlot** for the hot common
   cases.  Currently these are `(anonymous namespace)` functions but
   the profile shows they remain real calls.  Force-inline with
   `[[gnu::always_inline]]` and verify the asm.
3. **Specialise the loop-counter pattern** that drives `numeric_loop`:
   `for (let i = 0; i < N; i++) sum += i;` translates to a back-edge of
   OP_inc_loc + OP_lt + OP_jump_if_false.  Recognise this as a tight
   loop and emit a specialised single-step in the bytecode — or fuse
   at the dispatcher level.

**Expected yield**: 3–5 % of total wall time.  Should move
`numeric_loop` from 1.46× to roughly 0.8–1.0× vs QuickJS (parity / mild
win), and pull `control_flow` from 10.44× to roughly 4–6× vs QuickJS.

**Risk**: medium.  Integer fast paths are easy to specify but tight
loops live in correctness corners — overflow handling, NaN
propagation, strict-equality edge cases, double-vs-int comparison.
First PR should cover only `OP_add` and `OP_lt` between two
SmallIntegers, with explicit fallback for everything else.  Bench
coverage and Test262 coverage both needed.

**Prerequisites**: none.  Independent of the protoCore work above.
Can be developed in parallel.

**Concrete first PR**: `OP_add` and `OP_lt` SmallInteger fast paths
with overflow fallback.  Measure on `numeric_loop` — if it crosses
1.0× QuickJS, expand to `OP_sub`, `OP_le`, `OP_eq` in a follow-up.

## Expected combined impact

If all five land with the lower bounds of their yield estimates:

| optimisation | yield (% of total) |
|---|---:|
| P-JS-8 cell allocation | 5 % |
| P-JS-9 AVL list specialisation | 5 % |
| P-JS-10 shape-cached put_field | 3 % |
| P-JS-11 rope tag-bit fast paths | 1 % (concentrated in one bench) |
| P-JS-12 interpreter int-arith fast paths | 3 % |
| **combined (additive lower bound)** | **17 %** |

A 17 % across-the-board reduction would move the QuickJS geomean from
10.34× toward roughly 7–8×.  Upper-bound yield estimates put the
geomean closer to 5–6×.

The remaining gap beyond that is structural and likely requires either
(a) a JIT layer (significant effort), (b) per-shape attribute storage
(adjacent to P-JS-10 but a larger structural change), or (c) accepting
that interpreter-on-immutable-substrate has a hard ceiling and treating
the gap as the architectural cost of the design (the GIL-free advantage
on parallel_cpu is the offsetting return).

## Suggested order

```
P-JS-11  (independent, low-risk, fast win — useful for confirming
          the measurement pipeline)
P-JS-8   (foundational; everything else benefits from cheaper alloc)
P-JS-9   (depends on P-JS-8 for full effect)
P-JS-12  (independent; do in parallel with the alloc work)
P-JS-10  (depends on shape-id from P-JS-9 path)
```

P-JS-11 first because it's contained, low-risk, and produces a visible
win on a single bench — useful for confirming the perf measurement
pipeline.  P-JS-8 second because every later optimisation amortises
across cheaper allocation.  P-JS-12 can be developed concurrently with
P-JS-8 / P-JS-9 since it lives in the interpreter, not in protoCore.

## Methodology notes for future iterations

- `/tmp/protojs_perf_nogc/*.data` are the source perf records for this
  plan.  Preserve them as the baseline; recompare after each landed PR
  by re-running the same profiling script and diffing aggregates.
- **Always run profiling with `PROTOCORE_GC_CONTEXT_THRESHOLD=1e9`**
  unless the explicit purpose is GC analysis.  GC runs on a separate
  thread; mixing user-thread and GC-thread samples produces misleading
  symbol attribution.  GC-pressure analysis is its own session,
  separate from this one.
- Weight by absolute wall-time (`pct × bench_total_ms`), not by
  per-bench percentage, when picking targets.  A 10 % function in a
  500 ms bench moves the geomean less than a 5 % function in a 30 s
  bench.
- Kernel symbols (`[unknown] [k] ...`) are mostly page-fault and
  zero-fill costs downstream of allocation pressure.  They drop with
  P-JS-8/9 without needing direct kernel work.
- `[unknown]` user-space symbols are inline functions whose names were
  stripped by `-O3 -DNDEBUG`.  A future profiling pass should consider
  building with `-O3 -g -fno-omit-frame-pointer` to recover symbol
  attribution on those, before deciding any P-JS-13.

## Deferred: GC pressure analysis

This profile run deliberately suppressed GC to isolate single-thread
work.  The companion analysis — measuring how protoJS workloads stress
the GC thread, where mark/sweep cost goes, and what the optimal
context threshold looks like for each workload — is reserved for a
separate session.  Methodology for that session:

- Re-enable default GC threshold (`PROTOCORE_GC_CONTEXT_THRESHOLD`
  unset or `10000`).
- Profile with both threads sampled (`perf record` default behaviour)
  but record per-thread (`--sort=tid,symbol` on report).
- Enable `PROTOCORE_GC_PROFILE=1` for per-cycle phase timing.
- Cross-compare with this plan's user-thread numbers: any P-JS-N
  optimisation that reduces allocation pressure will also reduce GC
  thread load, so the two analyses are linked but measured separately.
